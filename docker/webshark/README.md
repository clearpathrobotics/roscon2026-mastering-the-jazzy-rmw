# Webshark: browser-based packet analysis for ROS 2 RMW traffic

Browser UI for inspecting `.pcap`, `.pcapng` and `.cap` captures with full RTPS/DDS and Zenoh protocol
decoding, purpose-built for debugging ROS 2 middleware behaviour. No host Wireshark
install, no X session. Everything runs inside Docker and a web browser.

## Why a custom image?

The upstream `qxip/webshark` image ships Wireshark 3.5. The Zenoh dissector
(`libzenoh_dissector.so`) requires the Wireshark 4.6 plugin ABI. Those are
incompatible, so this image:

1. Installs Wireshark 4.6 from the official PPA
2. Downloads and installs the zenoh-dissector 1.9.0 plugin
3. Patches `sharkd_dict.js` to translate the old Webshark frontend's request format
   to the JSON-RPC 2.0 protocol that sharkd 4.x expects
4. Adds `tshark`, Python, matplotlib, and pandas so capture-analysis scripts run
   inside the container, with no host tools required beyond Docker

A handful of small, targeted frontend patches ride on top of that (a Follow-Stream
UI bug, a file-list sort so the newest capture is easy to find, a manual Refresh
control for a capture that's still growing, a visible border/background on the
Statistics toolbar since the stock frontend ships it with none, and RMW-specific
one-click filter/graph presets). See `Dockerfile` for the exact patches; each one
documents what it's fixing and why in place.

## RTPS and Zenoh support

The three RMWs commonly used with ROS 2 Jazzy produce traffic Wireshark understands:

| RMW | Protocol | Wireshark dissector |
|-----|----------|---------------------|
| rmw_cyclonedds_cpp | RTPS over UDP | built-in `rtps` |
| rmw_fastrtps_cpp | RTPS over UDP | built-in `rtps` |
| rmw_zenoh_cpp | Zenoh over TCP/UDP | `zenoh-dissector` plugin |

Open a capture and you see individual RTPS frames (submessage types like `DATA`,
`HEARTBEAT`, `ACKNACK`, `GAP`, sequence numbers, writer/reader GUIDs) or Zenoh
message fields (`Push`, `Declare`, key expressions), not just raw bytes. DDS
reliability, discovery and QoS all happen at that layer. A metrics tool (Netdata,
`htop`, `iftop`) shows you that throughput went up. Only a wire-level decode shows
you whether that traffic was data, retransmits or discovery overhead.

## The guide

The container serves a standalone field guide at `/webshark/guide.html`, linked as **Guide**

The sections below summarise what the interface offers. The guide covers reaching a

Its screenshots live in `guide-assets/` and are regenerated by

## RMW presets: fast triage in a capture

A small panel above the packet list turns "read every packet" into "click and
see." It works on any capture from any of the three RMWs, not just this repo's
own demo captures.

Choose what a click should do first. **Packet list** narrows the packet list to
the matching frames. **Rate graph** plots that same filter over time in the
Advanced Graph. Every preset works in both modes, which is why five buttons cover
ten things. A discovery storm (participants restarting together, a flapping
link, a router bounce) is obvious as a spike in Rate and invisible in a filtered
list, so both stay one click apart.

Hovering any preset explains what it matches and what an empty result means.

**Discovery**: **SPDP** is participant announcements, the "who is on this network
at all" question. **SEDP** is endpoint announcements, the moment a writer's GUID
gets a topic name attached, which is where you find out whether a topic was ever
advertised. **Zenoh Declare** is Zenoh's equivalent, key expressions declared to
the router. An empty result usually means the capture missed the discovery window
rather than that the filter is wrong. Discovery fires when participants join, so
a capture started later has none in it. On this repo's own fleet,
`scripts/workshop observer capture bounce` replays it into the open capture.

**Repair**: **Retransmits** filters
`rtps.sm.acknack_analysis == 3 || tcp.analysis.retransmission`.
`rtps.sm.acknack_analysis` is Wireshark's own computed field for whether an
ACKNACK is reporting an actual gap, as opposed to a healthy periodic ack with
nothing missing. A plain `rtps.sm.id == 0x06` filter counts every ACKNACK
including the harmless ones and is mostly noise. One filter covers Cyclone and
Fast DDS together, since both speak RTPS, and `tcp.analysis.retransmission`
covers Zenoh the same way over TCP.

This only sees *reliable*-QoS traffic. This repo's own camera/scan topics are
best-effort by design (see
[lab2-on-the-wire/README.md](../../lab2-on-the-wire/README.md)), so on this
demo's own captures the signal is discovery-channel repair (DDS's built-in
participant/endpoint topics are reliable), not sensor-data repair. Seeing an
actual reliable user-data retransmit storm needs a reliable-QoS topic in the
traffic, which this demo doesn't currently publish.

**Fragments** filters `rtps.sm.id == 0x16`, the RTPS `DATA_FRAG` submessage a stack
emits when it splits a sample itself rather than handing an oversized datagram to
the kernel. Cyclone does that and Fast DDS does not, so on the same impaired
30-second window Cyclone reads 2595 and Fast DDS reads 0. A zero is the answer
rather than an empty filter, because it says the sample is crossing as IP
fragments, where losing any one of them costs the whole frame.

**Finding a common failure point**: click more than one preset in Rate mode. Each
adds its own coloured line to the same Advanced Graph on the same time axis
instead of replacing the last one, so a discovery spike and a retransmit spike
landing at the same timestamp is a real correlation rather than two things you
eyeball across separate views. Lines are named after the preset that drew them in
both the graph row and the chart legend, and clicking a legend entry hides that
line. **Clear Graphs** resets the panel back to one empty line, which stock
Webshark has no way to do otherwise.

**Reading the graph.** Check **Bucket** before reading anything into a shape. It
sets how much time each point covers, and sharkd's own default of one second is
too coarse for discovery. A whole SEDP exchange fires inside a single second, so
at that width it draws as one dot. Auto sizes the bucket from the capture's
length, aiming for a few hundred points, and labels the time axis with whatever
it chose. Narrow it by hand to see the shape of a burst, widen it to keep a long
capture readable.

**Axis** moves a line to a second Y scale on the right. Rates here differ by
orders of magnitude and a shared scale hides the smaller one. On this repo's own
`sedp_cyclone_bounce` capture, retransmits peak near 130 against SPDP near 850,
which draws the retransmit line flat along the bottom. On Y2 both shapes are
readable at once.

Drag on the chart to **zoom** into a time range. The strip underneath keeps
showing the whole capture, so where the zoomed window sits stays obvious.

**Capture summary**: opening any capture computes a one-line badge next to the
frame count, giving which RMW/vendor produced the traffic (from `rtps.vendorId`,
or `zenoh` as the protocol itself) and how many repair events it contains, using
the same filter as the Retransmits preset. It's a fast "what am I looking at, and
is anything obviously wrong" read before clicking anything else.

That same detection dims the presets the capture cannot answer, so SPDP and SEDP
fade on a Zenoh capture and Zenoh Declare fades on an RTPS one. Dimmed buttons
still work, and a dimmed preset returning zero is still an answer. A capture the
badge could not identify leaves everything at full strength rather than greying
out the whole panel.

Verify any of these display filters against the live dissector before using them
in front of a room. Filter syntax and field names drift across Wireshark
versions.

## Why not just desktop Wireshark?

Wireshark works fine on one machine, but it needs a per-seat install or an X
session, and plugin/version drift means two people can decode the same capture
differently. Webshark serves the same analysis in a browser: the RTPS and Zenoh
dissectors are baked into one image, so everyone decodes identically, and it works
headless, remote, or multi-machine without any client-side setup.

Most of desktop Wireshark's Statistics menu (Expert Info, Conversations/Endpoints,
an IO Graph) is not something you have to give up. That menu already ships in
Webshark's stock frontend and works through the sharkd bridge, it's just easy to
miss (no border/background on the toolbar row upstream, fixed in this image). Look
for it once you know it's there.

Protocol Hierarchy needed one addition. sharkd answers the request, but the stock
frontend has no renderer for that tap, so upstream the menu entry opens an empty
panel with no error. This image draws the table itself.

Note that RTPS gets its own row and Zenoh does not, so a Zenoh capture stops at
`tcp`. Zenoh is still decoding normally. Its layer shows up in `frame.protocols`
and in the detail pane, and only this breakdown misses it. Stock
`tshark -q -z io,phs` misses it too, so the gap is in the Zenoh plugin rather than
in Webshark. To confirm Zenoh decoded, use the Zenoh Declare preset or
`tap=conv:TCP`.

**Architecture: amd64 and arm64.** The image builds for whichever one the host is, with
no platform flag to set. amd64 remains the validated workshop target. arm64 decodes
identically to amd64, checked against every Zenoh capture in `lab2-on-the-wire/captures`.

Upstream publishes the zenoh dissector for x86_64 Linux only, so the arm64 build compiles
it from source. Expect roughly five minutes on a first build, cached afterwards.

Two caveats on arm64 hosts:

- **Jetson (L4T) cannot publish container ports.** `docker run -p` fails with
  `iptables: can't initialize iptables table 'raw'`, which the stock L4T kernel does not
  provide. Use `webshark.robot.yml`, which runs with `network_mode: host` and needs no
  port mapping. That is the right file on a robot anyway.
- **Docker Desktop on Apple Silicon is untested.** It should build natively now that the
  amd64 pin is gone, but nobody has run it.

If you cannot run this image on Apple Silicon, use desktop Wireshark instead. Install
4.6.x (current stable is 4.6.8, from
[wireshark.org/download.html](https://www.wireshark.org/download.html)), matching the
version this image's `Dockerfile` asserts. Then unzip the zenoh-dissector 1.9.0
release's `aarch64-apple-darwin.zip` asset into
`~/.local/lib/wireshark/plugins/4-6/epan` (a dash, not a dot, unlike the Linux path
this image uses). Apple Silicon then gets the same Zenoh decoding natively.

## Usage

Record a capture wherever the robot is, read it wherever you are. A capture is just a
file, so the machine that takes it and the machine that reads it need nothing to do with
each other.

```bash
# 1. on the robot, or anywhere the traffic is
sudo tcpdump -i <iface> -s 0 -w capture.pcap
#    tshark works too: sudo tshark -i <iface> -s 0 -a duration:60 -w capture.pcap

# 2. wherever you want to read it: the robot, a laptop, someone else's laptop
mkdir -p captures                       # first run only, see webshark.yml for why
cp /path/to/capture.pcap captures/
docker compose -f webshark.yml up -d
```

Then open `http://localhost:8085/webshark/`. `.pcap`, `.pcapng` and `.cap` all work, gzipped
or not, so whatever your capture tool produced can go straight in. Start with the
[guide](http://localhost:8085/webshark/guide.html), which ships in the image.

### No capture of your own yet

`fixtures/` holds fourteen recorded captures, ten of ROS 2 failing in a specific way and four
of it working, so you can learn the tool before you point it at a robot. Copy them into the
same directory:

```bash
cp fixtures/*.pcap.gz captures/
```

Each one is named for its symptom and paired with a section of the guide: a QoS mismatch, a
domain mismatch, a discovery storm, a node that dies, fragments that never reassemble, a Zenoh
router that is not there. [`fixtures/README.md`](fixtures/README.md) says what to filter on in
each and what you should see. They are also what the test suites in `tests/` read.

The two sections below are variations on this: the workshop's mock fleet generates the
traffic for you, and on a real robot you can capture from inside the same container.

## Using this in the ROSCon workshop

The workshop reads the fleet's own captures rather than `./captures`, which is what
`webshark.lab2.yml` is for. `scripts/workshop webshark up` layers it on automatically. By hand:

```bash
docker compose -f webshark.yml -f webshark.lab2.yml up -d
```

Compose replaces a bind mount by its target, so the overlay repoints `/captures` at
`lab2-on-the-wire/captures` instead of stacking a second mount on top.

The rest of this repo builds a mock ROS 2 fleet (an observer plus several mock
robots) to generate realistic RTPS/Zenoh traffic for the labs, and drives Webshark
against it. That's workshop-specific scaffolding, described in
[`lab2-on-the-wire/README.md`](../../lab2-on-the-wire/README.md) (the tool
walkthrough) and [`lab2-on-the-wire/beyond-the-wire/README.md`](../../lab2-on-the-wire/beyond-the-wire/README.md)
(the reference-only netem-ladder stress sweep), not part of Webshark itself. The generating code
for that sweep has been removed from the repository. `scripts/workshop observer capture start [N] [--streaming]`
runs a near-live capture written straight into Webshark's captures directory. Capture always starts
before any subscriber joins, since an RTPS
packet carries the writer's GUID rather than the topic name, and only the
discovery (SEDP) handshake at startup maps GUIDs back to topic names.

## Using this on a real robot

This covers webshark running on the robot itself under `webshark.robot.yml`, where
capture happens inside that container. `guide.html` section 4 covers both topologies and
is the version that ships in the image. What follows is the deployment detail behind it.

`scripts/workshop`'s subcommands are workshop-specific: they `docker exec` into named mock
containers (`observer`, `mock-robot-N`) that only exist in this repo's simulated
fleet. On a real robot, use `webshark.robot.yml` instead of `webshark.yml`.

`./capture-robot.sh` drives that loop. It checks the container can capture and is on
`network_mode: host`, asks which interfaces you are after, samples each candidate so you
can see which one is carrying traffic, and stops cleanly on Ctrl-C. It asks rather than
guessing because a ROS stack on the robot may be containerized itself, which puts the
traffic on a docker bridge or on loopback rather than on the robot's own network. The
network check is separate from the capability check because `CAP_NET_ADMIN` on a bridge
network fails quietly: the capture succeeds and records the bridge instead of the robot.
Guide section 4 carries the measured interface lists for both.

The script is also copied into the image at `/usr/local/bin/capture-robot.sh`, so a
deployment that never cloned this repo can lift it out with `docker cp`. Run it after
bringing the container up:

```bash
mkdir -p captures   # first run only, see webshark.robot.yml for why
docker compose -f webshark.robot.yml up -d
./capture-robot.sh
```

Nothing about `webshark.robot.yml` requires the script. By hand, that same loop is:

```bash
docker exec webshark ip -o -4 addr show          # pick the NIC by address, not by name
docker exec -it webshark tshark -i <iface> -s 0 -w /captures/robot-$(date +%Y%m%dT%H%M%S).pcap
```

The `-it` is not optional. Without a TTY, Ctrl-C kills the `docker` client and leaves
tshark running in the container writing to a file nobody is reading, and the image has no
`pkill` to recover with. Measured: the TTY-less form reached 6.5 MB before it was noticed,
while `-it` stopped on the first Ctrl-C and closed the file. Use `-a duration:120` for an
unattended capture. Timestamp the name, or the next run overwrites it.

Do the `mkdir` before the first `up`, not after. If compose gets there first it creates the
directory as root, the container runs as UID 1000, and the capture dies on
`Permission denied` once you are already past the interface question. `mkdir -p` will not
repair it afterwards, because the directory exists by then. Recover with:

```bash
sudo chown -R "$(id -u):$(id -g)" captures
```

That `tshark -i` only works under `webshark.robot.yml`, which is not interchangeable with
`webshark.yml`. The viewer configuration has no `CAP_NET_ADMIN`, and `dumpcap` carries
`cap_net_admin,cap_net_raw=eip`, so the exec fails outright:

```
tshark: Couldn't run dumpcap in child process: Operation not permitted
```

That message names neither the capability nor the compose file, so `docker exec -it webshark
bash` prints a banner saying which configuration is running, whether it can record, and where
captures actually live. The mount is `/captures`. The `captures/` directory sitting next to the
app inside the container is upstream's sample data and is not served.

`webshark.robot.yml` runs the container with `network_mode: host` and
`cap_add: [NET_RAW, NET_ADMIN]`. The same container that serves the browser UI on
`:8085` also captures directly on the robot's real interface (`eth0`, `wlan0`,
whatever NIC carries DDS/Zenoh traffic). There's no separate capture step and no
bare-host `tshark` install to keep in sync with the viewer.

Capturing itself doesn't need a specific Wireshark version: any `tshark` or
`tcpdump` on the host writes a standard `.pcap` that this image opens just as well,
and version only matters on the decode side. The `docker exec` workflow above is
recommended rather than required, since it means one less tool to install and
version-match on the robot.

Point `webshark.robot.yml`'s captures volume at wherever captures should land. It
ships with a placeholder path, not the workshop's `lab2-on-the-wire` default. The
container runs as a fixed non-root UID 1000 user, so if the host user's UID differs,
add `user: "$(id -u):$(id -g)"` to the service or chown the captures directory to
match.

`lab2-on-the-wire/scripts/lab2.sh`'s `_dds_iface()` auto-detects the capture interface through
`DDS_SUBNET`, which is hardcoded to this repo's flat mock bridge subnet (`172.31.0.x`).
That's why `scripts/workshop` itself doesn't generalize to a real robot. It isn't a limitation
of the `tshark -i` command above.
